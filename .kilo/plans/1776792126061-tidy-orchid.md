# Plan: Onboarding / Familiarity Reference — Milk Machine V5

> **Goal of this plan:** not to change any code, but to capture a concise,
> accurate mental model of the project so future tasks start from a shared,
> correct baseline. Use this as the canonical onboarding doc; update it as the
> project evolves.

---

## 1. What the project is

A home-made / converted calf milk-powder mixing and feeding machine controlled
by an **ESP32 (FireBeetle)**. Firmware is a PlatformIO / Arduino-framework C++
project. The ESP32 drives four **active-LOW** relays (auger, agitator, mixer,
water) in response to a single **level switch** input, with safety, reliability
and remote-monitoring features layered on top.

- **Board/env:** `firebeetle32` (platform `espressif32`, framework `arduino`)
- **Serial baud:** 115200
- **Upload:** OTA (`espota`) to `192.168.1.16:3232`
- **Key libs:** `ArduinoJson ^6.17.2`, `ESPAsyncWebServer-esphome ^3.1.0`
  *(declared but currently unused — the remote monitor uses the sync
  `WebServer` from the Arduino core)*

Entry point: `src/main.cpp:103` (`setup`) / `src/main.cpp:139` (`loop`).

## 3. Hardware I/O

Defined at `src/main.cpp:10-17`:

| Signal           | GPIO | Direction | Notes                                         |
|------------------|------|-----------|-----------------------------------------------|
| `RELAY_AUGER`    | 25   | OUT       | active-LOW                                     |
| `RELAY_AGITATOR` | 26   | OUT       | active-LOW                                     |
| `RELAY_MIXER`    | 16   | OUT       | active-LOW                                     |
| `RELAY_WATER`    | 17   | OUT       | active-LOW                                     |
| `LEVEL_SWITCH`   | 27   | IN_PULLUP | LOW = "milk needed"; debounce 50 ms            |

> ⚠️ **Doc drift:** `README.md` and `DEPLOYMENT.md` still say the level switch
> is on **GPIO12** (a strap pin, intentionally moved). Firmware is
> authoritative — pin is **GPIO27**. Flagged for future cleanup; not changing
> now.

Relays are presented to `OUTPUT` mode only **after** being driven HIGH, to
avoid a LOW glitch on boot turning everything on
(`presetOutputHigh()` in `src/main.cpp:160`). All writes go through a cached
writer `applyRelayState()` (`src/main.cpp:183`).

## 4. State machine

Enum `SystemState` at `src/main.cpp:30` and dispatcher `updateStateMachine()`
at `src/main.cpp:315`.

```
                 level LOW
        ┌──────────────────────┐
        ▼                      │
      IDLE ──(periodic 5m)──► PERIODIC_MIX ──(5s)──► IDLE
        │                       │
        │ level LOW              │ level LOW (demand during periodic)
        ▼                       ▼
      MIXING  ◄──────────────────┘
        │
        │ level HIGH (restored)
        ▼
      POST_MIX ──(5s)──► IDLE

   MIXING > 2 min       ──► FAULT
   heap < 8 KB          ──► FAULT
   sanity (>2m+10s)     ──► FAULT

   FAULT ──(60s cooldown)──► IDLE
   FAULT happens ≥3 times within 5 min window ──► esp_restart()
```

Relay combos per state:
- `MIXING` → **all four** relays on (`mixingRelaysOn()`).
- `POST_MIX`, `PERIODIC_MIX` → **mixer only** (`mixerOnlyOn()`).
- `IDLE`, `FAULT` → **all off** (`allRelaysOff()`).

### Key timing constants (`src/main.cpp:73-83`)
| Constant                   | Value     | Meaning                                   |
|----------------------------|-----------|-------------------------------------------|
| `POST_MIX_DURATION`        | 5 s       | mixer-only settle after demand-mix        |
| `PERIODIC_MIX_DURATION`    | 5 s       | stir length every interval                |
| `PERIODIC_MIX_INTERVAL`    | 5 min     | stir cadence when IDLE                    |
| `DEBOUNCE_STABLE_MS`       | 50 ms     | level-switch debounce window              |
| `WDT_TIMEOUT_SECONDS`      | 10 s      | esp_task_wdt timeout (panic = restart)    |
| `STATUS_INTERVAL`          | 10 s      | log status line cadence                   |
| `MAX_CONTINUOUS_MIX_MS`    | 2 min     | hard safety cap on MIXING                 |
| `FAULT_COOLDOWN_MS`        | 60 s      | before auto-leaving FAULT                 |
| `FAULT_WINDOW_MS`          | 5 min     | repeat-fault window                       |
| `MAX_FAULTS_BEFORE_REBOOT` | 3         | escalation threshold                      |

## 5. Reliability / safety features

- **Task watchdog:** `esp_task_wdt_init(10, true)` (`src/main.cpp:115`), reset
  every `loop()` iteration (`src/main.cpp:140`) and during OTA progress
  (`src/main.cpp:249`).
- **Boot cooldown:** if previous reset was WDT / brownout / power-on, force
  relays off and wait 500 ms (`src/main.cpp:127`).
- **Heap guard:** `MIN_SAFE_HEAP = 8192` — below that, `monitorHealth()`
  calls `enterFault("Low heap")` (`src/main.cpp:391`).
- **Fault escalation:** repeated faults inside `FAULT_WINDOW_MS` trigger a
  controlled `esp_restart()` (`src/main.cpp:308`).
- **Relay coalescing:** `applyRelayState()` only writes pins that change,
  eliminating needless toggles.
- **Strap-pin avoidance:** level switch moved off GPIO12 to GPIO27.

## 6. Networking & OTA

- **Mode:** `WIFI_STA`, static IP `192.168.1.16/24`, gateway `192.168.1.1`,
  DNS `1.1.1.1` / `8.8.8.8` (`src/main.cpp:23-27`).
- **Credentials (hardcoded):** SSID `"WiFi"`, pass `"Gliders1!"`
  (`src/main.cpp:20-21`). Future candidate for a secrets header.
- **Reconnect:** non-blocking with exponential backoff 30 s → up to 5 min
  (`handleWiFiOTA()` at `src/main.cpp:412`). Backoff resets on
  `SYSTEM_EVENT_STA_GOT_IP`.
- **OTA (`ArduinoOTA`):** hostname `"MilkMachine-V5"`, password `"Gliders1!"`.
  - Only serviced while `currentState == IDLE` AND WiFi connected
    (`src/main.cpp:414`).
  - `onStart` forces `allRelaysOff()`.
  - `ArduinoOTA.begin()` is called both in `initializeOTA()` at boot and in
    the `GOT_IP` handler — minor duplication, noted.
- **WiFi event hook** `onWiFiEvent()` (`src/main.cpp:195`): starts OTA and
  `RemoteMonitor` on connect, stops `RemoteMonitor` on disconnect.

## 7. Remote monitoring

Implemented in `src/remote_monitor.{h,cpp}` + `src/monitor_config.h`.

- **TCP server** on `MONITOR_TCP_PORT` (default **23**, telnet-style). Up to
  `MONITOR_MAX_CLIENTS = 2` simultaneous raw clients; each new connect slots
  into a free/disconnected seat, or is refused with `"Server full"`.
- **HTTP server** on `MONITOR_WEB_PORT` (default **80**, sync `WebServer`).
  - `/`  → auto-refreshing (5 s) HTML log viewer.
  - `/logs` → plain-text dump of the in-RAM ring buffer.
  - HTTP Basic auth (`admin` / `MONITOR_PASSWORD`) behind
    `#if MONITOR_ENABLE_AUTH`.
- **Log buffer:** single `String` capped at `MONITOR_LOG_BUFFER_SIZE = 4096`
  bytes; oldest lines trimmed by `indexOf('\n')` rolling window.
- **Log tees:** use the macros — every important message already uses them.
  ```cpp
  RLOG_PRINTLN("STATE: IDLE -> MIXING ...");
  RLOG_PRINTF("Fault count ...: %u\n", faultCount);
  ```
  Macros write to `Serial` unconditionally and to the monitor only if
  `enabled`.
- **Lifecycle:** started on `GOT_IP`, stopped on `DISCONNECTED` — the monitor
  never holds resources while offline.
- **Unused-but-declared settings** in `monitor_config.h`:
  `MONITOR_AUTO_RESTART_ON_HANG`, `MONITOR_RESTART_DELAY_MS`,
  `MONITOR_MAX_CONNECTIONS_PER_MINUTE`, `MONITOR_ENABLE_RATE_LIMITING`. These
  are not wired up yet; they're aspirational.

**Client-side helper:** `test_monitor.py` — runs TCP + HTTP smoke tests or a
continuous TCP tail (`python test_monitor.py monitor`).

## 8. Loop() anatomy

Order of operations per iteration (`src/main.cpp:139-157`):

1. `esp_task_wdt_reset()` — keep the dog fed.
2. `serviceInputs()` — sample + debounce the level switch.
3. `updateStateMachine()` — drive relays according to state.
4. `monitorHealth()` — heap + mixing-sanity check.
5. `handleWiFiOTA()` — reconnect-backoff + `ArduinoOTA.handle()` if safe.
6. `remoteMonitor.handle()` — accept TCP clients, service HTTP.
7. Every `STATUS_INTERVAL` ms → `printSystemStatus()`.

No blocking calls outside of the one-shot boot `delay(500)` after a dirty
reset — everything else is cooperative.

## 9. Known caveats / gotchas (reference, not fix)

1. `README.md:8` and `DEPLOYMENT.md` level-switch pin is stale (says 12, is 27).
2. `ESPAsyncWebServer-esphome` listed in `platformio.ini:24` but not used;
   current monitor uses the sync `WebServer`.
3. `ArduinoOTA.begin()` is called twice — once in `initializeOTA()` and once
   in the `GOT_IP` event. Harmless in practice.
4. `lastFaultTimestamp` initializes to 0; a very-first fault at high millis
   may briefly miscount the window (edge case, self-corrects).
5. WiFi/OTA passwords are hardcoded — not a secret-management scheme.
6. Web UI uses HTML refresh polling, not SSE / WS; fine for casual use.
7. `monitor_config.h` has four feature flags declared but not implemented yet.
8. `data/`, `include/`, `lib/`, `test/` are empty — ready for future assets,
   headers, libraries, and PlatformIO native-env unit tests respectively.

## 11. Ready for real work

When a concrete task lands, we already know:

- where to wire new logic in the state machine (`updateStateMachine()`),
- how to log safely to both serial + remote (`RLOG_PRINTLN` / `RLOG_PRINTF`),
- how to add/adjust relays (`applyRelayState()` + new helper like
  `mixingRelaysOn()`),
- how to add a new web route (attach to `webServer` in
  `RemoteMonitor::begin()`),
- how to add a new safety trip (extend `monitorHealth()` →
  `enterFault("why")`),
- that OTA will only run when `IDLE` + connected — any new state must be
  considered for OTA-safety.

This doc is intentionally implementation-neutral. Real changes will get their
own plan files.
